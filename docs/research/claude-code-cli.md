## 1. Architecture: what the harness is

Claude Code is "an agentic harness around Claude: it provides the tools, context management, and execution environment that turn a language model into a capable coding agent." The model does all reasoning and tool selection; the harness owns tool execution, permissions, hooks, persistence, and context assembly. [DOCUMENTED] [src: how-it-works]

The loop has three blended phases — gather context, take action, verify results — repeated until the task completes, with the user able to interrupt at any point (Esc cancels the running tool call; typing a correction and pressing Enter queues it without stopping the current action, and the model reads it before deciding its next step). [DOCUMENTED] [src: how-it-works]

The built-in tool roster (the names the model actually calls, as enumerated by the PreToolUse matcher documentation): `Bash`, `Edit`, `Write`, `Read`, `Glob`, `Grep`, `Agent`, `WebFetch`, `WebSearch`, `AskUserQuestion`, `ExitPlanMode`, plus MCP tools under `mcp__<server>__<tool>` naming. Older harness versions exposed the subagent dispatcher as `Task`; current versions expose it as `Agent` — this repo's hooks match `Task|Agent` precisely to absorb that rename. [DOCUMENTED/OBSERVED] [src: hooks-pretooluse] [src: muster-hooks-json]

The harness is a single native executable, not a wrapper script: `file` on the installed binary shows an ELF executable containing a full bun/esbuild single-file JS/TS compile (~250 MB), which embeds its own ripgrep, its OS-sandbox runtime hooks, a markdown/mermaid renderer, and the entire permission/hook/session machinery; there is no separate daemon — one `claude` process is the whole harness for a session. Builds live at `~/.local/share/claude/versions/<semver>` with `~/.local/bin/claude` a symlink to the active one, and `claude update|upgrade` installs new builds. [OBSERVED] [src: binary-nature]

The binary's own tool-definition strings confirm a broader registry than the PreToolUse matcher list exposes. Core tools present in a bare zero-plugin session also include `NotebookEdit` (Jupyter cells), `KillShell`/`BashOutput` (manage a backgrounded shell), `Skill` (invoke a packaged skill), `TodoWrite` (the model-managed task-list state that predates the `TaskCreate`/`TaskUpdate` board — see §6), and `ToolSearch` (§8). Beyond that "naked" set the same binary implements an **extended agent-teams / scheduling surface** — `SendUserMessage`, `SendUserFile`, `PushNotification`, `Monitor`, `ScheduleWakeup`, `TaskList`/`TaskCreate`/`TaskGet`/`TaskUpdate`/`TaskStop`/`TaskOutput`, `EnterWorktree`/`ExitWorktree`, `Workflow`, `ListAgents`, `CronCreate`/`CronDelete`/`CronList`, `ConnectGitHub`, `SendMessage`, `StructuredOutput`, `WaitForMcpServers`, `RefreshMcpTools`, `EndConversation` — reached through background-agent and agent-team modes (the `claude agents` subcommand, §11), not the single-session loop. `--tools "Bash,Edit,Read"` restricts the built-in set for a session, `--tools ""` disables all tools, `--tools default` restores everything. The native primitive for a self-continuing loop that a `disable-model-invocation: true` command CAN ride is `/goal`, not `/loop`. `/goal <condition>` (a distinct built-in, requires v2.1.139+) sets a completion CONDITION that the session's small fast model re-checks after every turn, starting another turn until the condition holds and then clearing itself — session-scoped, and internally a wrapper around a prompt-based Stop hook. Where `/loop` re-fires on a TIME INTERVAL, `/goal` re-runs on a CONDITION; its own comparison table lists the two side by side (`/goal` = "the previous turn finishes" / "a model confirms the condition is met"; `/loop` = "a time interval elapses"). `/goal` re-runs the condition, not a command invocation, so the `disable-model-invocation` scheduled-fire restriction above does not touch it — confirming `/goal` as a real, distinct native primitive rather than a conflation with `/loop`. ## 2. The agent loop: turn structure and context management

### 2.1 Turn structure

The hook cadence documents the real loop shape: `SessionStart`/`SessionEnd` fire once per session; `UserPromptSubmit`, `Stop`, and `StopFailure` fire once per turn; `PreToolUse` and `PostToolUse` fire "on every tool call inside the agentic loop." A turn is therefore: user prompt → repeated (model call → tool batch → results appended) → model stops → `Stop` event. [DOCUMENTED] [src: hooks-lifecycle]

`PostToolBatch` fires "after a full batch of parallel tool calls resolves, before the next model call" — direct evidence that the harness executes the model's parallel tool_use blocks as a batch, joins on all of them, and only then issues the next API request. Exit code 2 from a PostToolBatch hook "stops the agentic loop before the next model call," which is the documented seam for halting the loop mid-turn. [DOCUMENTED] [src: hooks-exit-codes]

Tool results re-enter context as tool-result messages appended to the conversation; hook-injected `additionalContext` for `PreToolUse`/`PostToolUse`/`PostToolBatch` is delivered "next to the tool result," wrapped in a system reminder that the model reads on the next request but that never renders as a chat message. [DOCUMENTED] [src: hooks-additional-context]

Messages are Anthropic Messages-API-shaped end to end, verified against a live transcript: an assistant message's `content` is an array of typed blocks — `thinking` (carries an opaque `signature`, not just text), `text`, and `tool_use` (note the `caller` field, e.g. `{"type":"direct"}`, distinguishing model-issued calls from dispatched/forked ones) — and each tool result travels back as a `{"type":"tool_result","tool_use_id":...,"is_error":...}` block inside the *next* user-role message. The loop repeats until an assistant message carries a `stop_reason` other than `tool_use`, at which point `Stop` fires. In print mode, `--include-partial-messages` (with `stream-json`) exposes partial-message deltas as they arrive, and `--forward-subagent-text` surfaces subagent text/thinking as parent-tagged messages via `parent_tool_use_id`. [OBSERVED] [src: live-transcript] [src: live-help]

Large outputs are spilled rather than injected: hook output strings (including `additionalContext` and stdout) are capped at 10,000 characters, and overflow "is saved to a file and replaced with a preview and file path, the same way large tool results are handled." [OBSERVED] in this session: oversized MCP results were written to `~/.claude/projects/<project>/<session-id>/tool-results/<id>.txt` and replaced in-context by a preview plus the file path. MCP outputs get their own budget: a warning at 10,000 tokens, a default cap of 25,000 tokens (`MAX_MCP_OUTPUT_TOKENS`), a per-tool override via `_meta["anthropic/maxResultSizeChars"]` up to a 500,000-character hard ceiling, past which "results ... are persisted to disk and replaced with a file reference in the conversation." [DOCUMENTED] [src: hooks-json-output] [src: mcp-output-limits] [src: claude-directory]

### 2.2 What loads before the first prompt

Startup context assembly, in documented order: the system prompt (plus output style and any `--append-system-prompt` text), then CLAUDE.md files (managed → user `~/.claude/CLAUDE.md` → project `./CLAUDE.md` or `./.claude/CLAUDE.md` → `CLAUDE.local.md`, walking up the directory tree with root-most first and local-most last), unscoped `.claude/rules/*.md`, auto memory (first 200 lines or 25KB of `MEMORY.md`, whichever comes first), skill names+descriptions, and MCP tool names (schemas deferred — see §7). CLAUDE.md content "is delivered as a user message after the system prompt, not as part of the system prompt itself." Subdirectory CLAUDE.md files and path-scoped rules load lazily when Claude reads matching files. [DOCUMENTED] [src: context-window] [src: memory-page]

CLAUDE.md supports `@path/to/import` expansion at launch (max depth 4 hops, code spans skipped, external imports gated by a one-time approval dialog), and block-level HTML comments are stripped before injection. [DOCUMENTED] [src: memory-page]

The system prompt is assembled, not a single static string: the binary carries three coexisting identity literals selected by launch context — `"You are Claude Code, Anthropic's official CLI for Claude."` (interactive), `"...running within the Claude Agent SDK."` (SDK-hosted), and `"You are a Claude agent, built on Anthropic's Claude Agent SDK."` (headless/agent — the variant a dispatched research subagent sees) — which partially fills the §Coverage-gaps note that the full prompt text is unpublished: the identity lines, at least, are recoverable. The per-machine dynamic block (cwd, environment info, git branch/status/recent commits) loads as a separate section at the very end of the system prompt; `--exclude-dynamic-system-prompt-sections` relocates those bits into the first user message instead, specifically to improve cross-user prompt-cache reuse. [OBSERVED] [src: binary-identity] [src: live-help]

### 2.3 Compaction

When context approaches the limit, the harness "clears older tool outputs first, then summarizes the conversation if needed"; if a single oversized item makes context refill immediately after each summary, auto-compaction stops after a few attempts and surfaces a thrashing error instead of looping. [DOCUMENTED] [src: how-it-works]

Compaction is observable and blockable: `PreCompact` fires with matcher `manual` (`/compact`) or `auto`, receives `trigger` and `custom_instructions` (the argument to `/compact` for manual, empty for auto), and exit 2 or `{"decision": "block"}` blocks it — with the documented nuance that blocking a proactive auto-compact continues uncompacted, while blocking a recovery compact (triggered by a context-limit error already returned by the API) lets the underlying error surface and the request fail. `PostCompact` receives `compact_summary`, the generated summary text, and has no decision control. [DOCUMENTED] [src: hooks-precompact]

What survives compaction is specified per mechanism: system prompt and output style unchanged (not message history); project-root CLAUDE.md, unscoped rules, and auto memory re-injected from disk; path-scoped rules and nested CLAUDE.md lost until a matching file is read again; invoked skill bodies re-injected but capped at 5,000 tokens per skill and 25,000 tokens total, oldest dropped first; hooks unaffected (they run as code, not context). The summarization request inherits the session's extended-thinking configuration (v2.1.198+). [DOCUMENTED] [src: context-window]

Steering knobs: `/compact <focus>` and a "Compact instructions" section in CLAUDE.md shape the summary; `/clear` resets the session entirely (and fires `SessionStart` with `source: "clear"`); `/context` shows a live per-category breakdown. Compaction also fires `SessionStart` with `source: "compact"`, so session-start hooks can re-inject context that summarization dropped. [DOCUMENTED] [src: costs-page] [src: hooks-sessionstart]

Mechanism details corroborated across the binary and docs: the auto path is gated by `autoCompactWindow` (a token threshold in `settings.json`, tunable via `/autocompact`); the summary can be **precomputed in the background** before the hard threshold and swapped in synchronously only if a "prompt too long" condition fires, so it is not always on the blocking path; a PreCompact veto surfaces the literal runtime error `"Compaction blocked by PreCompact hook"`; and compaction is not always a full replace — it can preserve a tail of recent messages (`preserved_messages`, with an `anchor` marking where preserved content begins) and summarize only the middle. One injection-safety consequence the docs call out: the auto-mode classifier reads conversational "boundaries" (e.g. a spoken "don't push yet") straight from the live transcript, so a stated boundary can be silently lost if compaction drops the message that stated it — the docs recommend a hard `deny` rule over relying on a spoken boundary surviving compaction. [OBSERVED/DOCUMENTED] [src: binary-compaction] [src: docs-auto-mode]

## 3. Tool dispatch and the permission model

### 3.1 Permission system

The base permission posture is tiered: read-only tools need no approval inside the working directory and `additionalDirectories`; Bash requires approval except for a built-in read-only command set, and a permanent "don't ask again" approval is saved per repository and command; file modifications require approval that persists until session end. Permanent approvals are written to `.claude/settings.local.json` at the git repository root, "resolved through worktrees to the main checkout," so one file covers every worktree of the repo. [DOCUMENTED] [src: permissions-system]

Permission rules use `Tool` or `Tool(specifier)` syntax and are evaluated deny → ask → allow, first match wins, specificity irrelevant — a broad deny cannot carry narrow allow exceptions. A bare tool-name deny (`Bash`) removes the tool from the model's context entirely; a scoped deny (`Bash(rm *)`) leaves the tool visible and blocks matching calls. Rules are "enforced by Claude Code, not by the model" — prompts and CLAUDE.md shape intent but never capability. [DOCUMENTED] [src: permissions-manage]

The `permissions` settings object carries `allow`, `ask`, `deny` (rule arrays), `additionalDirectories`, `defaultMode`, and `disableBypassPermissionsMode`; deny examples in the official docs include `WebFetch`, `Bash(curl *)`, `Read(./.env)`, and `Read(./secrets/**)`. [DOCUMENTED] [src: settings-permissions]

Permission modes (cycled with Shift+Tab, set via `defaultMode` or `--permission-mode`): `default` (prompt on first use; labeled Manual), `acceptEdits` (auto-approve edits plus common filesystem commands like `mkdir`/`touch`/`mv`/`cp` on in-scope paths), `plan` (read-only exploration), `auto` (a background classifier model reviews actions), `dontAsk` (auto-deny anything not pre-approved), and `bypassPermissions` (skip prompts, except explicit ask rules, org-required approvals, and an `rm -rf /`-class circuit breaker that still prompts). A repo cannot grant itself `auto` via project settings. [DOCUMENTED] [src: permissions-modes] [src: settings-permissions]

Project-supplied capability is trust-gated: `permissions.allow` and `additionalDirectories` in a project's `.claude/settings.json` apply only after the user accepts the workspace-trust dialog for that workspace (keyed on the git repo root); deny/ask rules apply regardless because they only restrict. [DOCUMENTED] [src: permissions-trust]

The `auto` mode is a distinct, newer overlay rather than one of the four classic modes: a server-selected **classifier model** (independent of the session's own `/model`) reviews every action that is not a plain read or an in-scope working-directory edit. It sees user messages, tool calls, and CLAUDE.md, but tool *results* are deliberately stripped from what it sees, so hostile content fetched mid-task cannot manipulate the classifier directly (a separate server-side probe scans incoming results for that). Decision order: (1) explicit allow/ask/deny rules resolve immediately — except protected-path writes and org-`ask`-marked connector/MCP tools always route to a human prompt regardless of an allow match; (2) in-scope reads/edits auto-approve; (3) everything else goes to the classifier, which can block with a reason fed back to the model. If it blocks 3 times consecutively or 20 times total in a session it **pauses itself** and reverts to interactive prompting (not configurable); in headless `-p` mode with no human, repeated blocks abort the run. Auto mode requires model+provider+plan eligibility and cannot be granted by project/local settings. [DOCUMENTED] [src: docs-auto-mode]

`manual` is an accepted alias for `default` everywhere, and `default` is labeled **Manual** in every UI. A fixed set of **protected paths** — `.git`, `.claude` (except `.claude/worktrees`), `.vscode`, `.idea`, `.husky`, shell rc files, `.npmrc`, `.mcp.json`, `.claude.json` and similar — is never auto-approved for writes in any mode except `bypassPermissions`, and a `permissions.allow` entry cannot override this because the protected-path check runs *before* allow-rule evaluation. Writes to Claude Code's own `settings.json` at every scope are denied even inside the sandbox (symlink targets included, v2.1.210+). [DOCUMENTED] [src: docs-auto-mode] [src: docs-protected-paths]

### 3.2 Hook lifecycle

Hooks are "user-defined shell commands, HTTP endpoints, or LLM prompts that execute automatically at specific points in Claude Code's lifecycle." Configuration is three-level: event → matcher group → handler list, defined in `~/.claude/settings.json`, `.claude/settings.json`, `.claude/settings.local.json`, managed policy, plugin `hooks/hooks.json`, or skill/agent frontmatter. [DOCUMENTED] [src: hooks-ref] [src: hooks-locations]

Handler types are `command` (JSON on stdin, results via exit code + stdout), `http` (JSON as POST body, results via response body), `mcp_tool`, `prompt` (single-turn LLM yes/no), and `agent` (a tool-using subagent verifies conditions; experimental). All matching handlers run in parallel and identical handlers are deduplicated. [DOCUMENTED] [src: hooks-handlers]

Matcher semantics: `"*"`/empty/omitted matches all; a value containing only letters, digits, `_`, `-`, spaces, `,`, `|` is an exact string or `|`/`,`-separated list; anything else is an unanchored JavaScript regex tested with `RegExp.prototype.test` (so `Edit.*` also matches `NotebookEdit`; anchor with `^...$` for whole-string). Tool events match on `tool_name`; `SessionStart` matches on how the session started (`startup`, `resume`, `clear`, `compact`); `PreCompact`/`PostCompact` on `manual`/`auto`; `SubagentStart`/`SubagentStop` on agent type. [DOCUMENTED] [src: hooks-matchers]

Exit-code contract: exit 0 = success and stdout is parsed for JSON output fields (for most events stdout goes to the debug log; for `UserPromptSubmit`, `UserPromptExpansion`, and `SessionStart` stdout becomes model-visible context); exit 2 = blocking error, stdout/JSON ignored, stderr fed back (blocks the tool call for PreToolUse, rejects the prompt for UserPromptSubmit, prevents stopping for Stop); any other exit code = non-blocking error, execution continues. Notably exit 1 does not block — policy hooks must use exit 2. [DOCUMENTED] [src: hooks-exit-codes] The exit-0 plain-text-as-context path is narrow: for events other than `SessionStart`, `Setup`, and `SubagentStart`, non-JSON stdout on exit 0 is silently discarded (debug-logged only). And the *field* that carries a veto differs by event family: PreToolUse uses `hookSpecificOutput.permissionDecision`, whereas the "block" family (`PostToolUse`, `Stop`, `SubagentStop`, `PreCompact`, …) uses a top-level `decision: "block"`. [OBSERVED] [src: binary-events]

The full lifecycle is broader than the cadence summary above: **31 named hook events** exist in the 2.1.211 build (confirmed both in the binary's literal event-name strings and the fetched docs). Beyond the events already discussed, the set includes `Setup` (`--init-only`/maintenance), `UserPromptExpansion`, `PermissionRequest`/`PermissionDenied`, `PostToolUseFailure`, `Notification`, `MessageDisplay`, `SubagentStart`/`SubagentStop`, `TaskCreated`/`TaskCompleted`, `Stop`/`StopFailure`, `TeammateIdle` (agent-team), `InstructionsLoaded`, `ConfigChange`, `CwdChanged`, `FileChanged`, `WorktreeCreate`/`WorktreeRemove`, `PreCompact`/`PostCompact`, `Elicitation`/`ElicitationResult` (MCP user-input), and `SessionEnd`. A subset support no matcher and always fire (`UserPromptSubmit`, `PostToolBatch`, `Stop`, `TeammateIdle`, `TaskCreated`, `TaskCompleted`, `WorktreeCreate`, `WorktreeRemove`, `MessageDisplay`, `CwdChanged`); several cannot block regardless of exit code (`SessionStart`, `PostToolUse`, `PermissionDenied`, `Notification`, `PostCompact`, `SessionEnd`, `StopFailure`). [OBSERVED] [src: binary-events] **SUPERSEDED by §13.3:** current docs list 34 events (adds `DirectoryAdded`, `PreModelSwitch`, `PostModelSwitch`), and handlers gained `onFailure` (2.1.295). `TaskCreated` no longer fires in sessions without the Task tools, which is the default on current models.

Two further handler mechanics matter for a reimplementation: a hook can defer its verdict with `"async": true` (backgrounds it without blocking the loop) and `"asyncRewake": true` (additionally wakes the session when the backgrounded hook later exits 2, injecting its output as a system reminder) — i.e. a hook can interrupt the session later rather than holding it up front; and an individual handler can be scoped with an `"if": "Bash(git push *)"` permission-rule predicate so it only runs for matching calls. Command handlers in exec form (`args: []`) skip the shell entirely, versus shell form which gets full tokenization/pipes/expansion; `${CLAUDE_PROJECT_DIR}`, `${CLAUDE_PLUGIN_ROOT}`, and `${CLAUDE_PLUGIN_DATA}` are available as both placeholders and env vars. The read-only `/hooks` command browses every configured hook by source (User/Project/Local/Plugin/Session/Built-in). [DOCUMENTED] [src: docs-hooks-async]

Common input fields delivered as JSON on stdin: `session_id`, `prompt_id` (UUID of the current user prompt, v2.1.196+), `transcript_path` (path to the session's JSONL; written asynchronously and may lag the in-memory conversation), `cwd`, `permission_mode` (`"default"`, `"plan"`, `"acceptEdits"`, `"auto"`, `"dontAsk"`, `"bypassPermissions"`), `effort` (`{level}`), and `hook_event_name`; tool events add `tool_name` and `tool_input`; inside subagents two more fields appear: `agent_id` ("present only when the hook fires inside a subagent call") and `agent_type`. ### 3.3 PreToolUse decision control — the enforcement seam

PreToolUse returns decisions inside `hookSpecificOutput`: `permissionDecision` is one of `"allow"` (skip the prompt), `"deny"` (block; reason shown to Claude), `"ask"` (force a prompt; reason shown to the user), or `"defer"` (headless-only pause/resume); `permissionDecisionReason` carries the message; `updatedInput` replaces the entire tool input object before execution; `additionalContext` rides alongside the eventual tool result. Settings-level deny and ask rules are still evaluated regardless of what a hook returns, and when multiple hooks disagree the precedence is deny > defer > ask > allow. A hook `"ask"` also forces a prompt in auto mode — the classifier can still deny but cannot silently approve. [DOCUMENTED] [src: hooks-decision]

This repo's wave-guard hook emits exactly this shape in production — `{"hookSpecificOutput": {"hookEventName": "PreToolUse", "permissionDecision": "deny", "permissionDecisionReason": ...}}` to deny, and `{"hookSpecificOutput": {"hookEventName": "PreToolUse", "additionalContext": ...}}` for a warn-but-allow — and is deliberately fail-open (any exception → silent allow), because a false deny teaches users to disable guards globally. ### 3.4 Bash sandboxing — an OS-level axis independent of permissions

Sandboxing is a separate enforcement layer from the permission system: OS-level containment scoped to the `Bash` tool and its child processes only — `Read`/`Edit`/`Write` go through the permission system directly and are never sandboxed. Mechanism by platform: macOS uses Seatbelt (`sandbox-exec`, no extra install); Linux/WSL2 use `bubblewrap` (filesystem) + `socat` (network relay) + an optional seccomp filter via `@anthropic-ai/sandbox-runtime`; native Windows is unsupported (run inside WSL2). [DOCUMENTED] [src: docs-sandboxing] [src: binary-sandbox]

Default boundary: read/write to cwd + the session `$TMPDIR`; read access to everything else on disk except explicit deny paths (note that default read access still includes credential files like `~/.aws/credentials` and `~/.ssh/` unless `sandbox.credentials` denies them — sandboxing does not blanket-protect secrets); zero network domains pre-allowed, first use of a new domain prompts once per session (or is silently blocked under `allowManagedDomainsOnly`). The settings schema is extensive — `sandbox.enabled`, `sandbox.failIfUnavailable`, `sandbox.allowUnsandboxedCommands`, `sandbox.autoAllowBashIfSandboxed`, `sandbox.filesystem.{allowRead,allowWrite,denyRead,denyWrite}`, `sandbox.network.{allowedDomains,deniedDomains,httpProxyPort,socksProxyPort,tlsTerminate}`, `sandbox.credentials.{files,envVars}` (per-entry `mode: deny|mask`), `excludedCommands`. A per-call `dangerouslyDisableSandbox: true` tool parameter retries a sandbox-incompatible command through the *regular* permission flow (auto-mode's classifier still reviews it); `allowUnsandboxedCommands: false` is strict mode that disables that hatch. Two circuit breakers survive even `bypassPermissions`/auto-allow: `rm -rf /`-shaped deletes always prompt, and writes to Claude Code's own `settings.json` are always denied. Sandbox and permission mode are explicitly two axes — `--dangerously-skip-permissions` skips both prompt layers but not the OS boundary if sandboxing is separately enabled; subagents run in the same process and inherit the parent's sandbox config verbatim. [DOCUMENTED] [src: docs-sandboxing] [src: binary-sandbox]

## 4. Sessions: persistence, resume, and the transcript

Every session is persisted as plaintext JSONL — "each message, tool use, and result is written to a plaintext JSONL file under `~/.claude/projects/`" — which is what enables rewinding, resuming, and forking. The on-disk addressing scheme, confirmed on this machine: `~/.claude/projects/<slug>/` where `<slug>` is the cwd's absolute path with `/` replaced by `-` (`/home/ryan/dev/muster` → `-home-ryan-dev-muster`), one directory per distinct cwd, holding `<session-id>.jsonl` plus a same-named sidecar directory with `subagents/agent-<id>.jsonl` (+ `agent-<id>.meta.json` carrying `{agentType, description, toolUseId, parentAgentId, spawnDepth}`) and `tool-results/<token>.txt` spill files. [DOCUMENTED] [src: subagents-config]

Context isolation is the point of a subagent, per the official context-window walkthrough: a subagent gets its **own context window** (not a continuation of the parent's), with its own shorter system prompt, its own copy of project CLAUDE.md counted against its budget, and the **same** MCP servers and skills as the parent — minus a few tools that make no sense nested (plan-mode controls, background-task tools, and by default the `Agent` tool itself, to bound recursion). When names collide, resolution is managed settings > `--agents` CLI JSON > project (closest-to-cwd nested dir wins) > user > plugin, and a custom name shadows a same-named built-in. Under auto mode, a subagent's actions are re-checked by the classifier at three points — before spawn (on the task description itself), during execution, and a return-scan that can prepend a security warning to its results — and any `permissionMode` set in the subagent's own frontmatter is **ignored** (a plugin-shipped agent may not set it at all). **Dispatch surface changes.** 2.1.212: "Deprecated the Task tool's `mode` parameter (now ignored); subagents inherit the parent session's permission mode by default" (muster never passed it); "Reduced token usage in inter-agent messaging: `SendMessage` bodies are no longer duplicated into replayed history and tool results"; `/fork` became a background-session copy and the old in-session fork is `/subtask`. 2.1.218: "Changed skills with `context: fork` to run in the background by default; opt out per skill with `background: false`" and `/code-review` now runs as a background subagent. 2.1.216: worktree-isolated subagents can no longer redirect git at the shared checkout via `git -C`/`--git-dir`/`GIT_DIR` (isolation hardening). 2.1.210: "Hardened the Agent tool against indirect prompt injection via content a subagent read."

**Models.** 2.1.219: "Added Claude Opus 5 (`claude-opus-5`), now the default Opus model — 1M context, fast mode at $10/$50 per Mtok"; Opus 4.7 removed from fast mode. The Claude adapter's aliases float (`prime → opus` now resolves to Opus 5); no muster change required.
