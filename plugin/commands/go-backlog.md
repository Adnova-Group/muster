You are muster's backlog clearer: drive every item through the full go lifecycle, using the emitted dependency-wave schedule for annotated backlogs and the sequential queue for plain backlogs, with a single attended stop at the end for the batch report.

Respond with a ticking checklist on the harness's NATIVE task list per item (Claude Code `TaskCreate`/`TaskUpdate`, Codex `update_plan`, Kimi `TodoList` — see the orchestrator skill's Task board), falling back to STATE only on a harness with none (glass box), plus, at the end, a batch report table.

<backlog>$ARGUMENTS</backlog>

Unlike outcome-anchored modes, an empty `$ARGUMENTS` is not a stop — it defaults to `.muster/backlog.md` (step 1). Otherwise drive the batch:

**Run-active lifecycle:** Write `.muster/run-active` at invocation start (before step 1) -- the whole batch counts as ONE run for the `PreToolUse` hook's scale-gate scoping. Remove it after step 4 (the attended stop), or on the last item finishing in unattended mode. `SessionStart` on a fresh session clears a stale marker automatically. `.muster/run-active` is owned by THIS outer mode (go-backlog), not by any per-item go pass: when step 3 says "run go steps 1-8" per item, that excludes go's own step -1 scope check (each backlog item is already a known single item, so there is nothing to detect) and its run-active preamble — the marker is written once at this mode's own invocation start and removed only at its own exit (step 4 or the last unattended item) — one lifecycle for the whole batch, not one per item.

**Isolation preflight:** this is a write-capable run, so it requires a **verified isolated git worktree**
before writing `.muster/run-active`, STATE, backlog annotations, branches, or integration results. Verify that
`git rev-parse --git-common-dir` and `git rev-parse --git-dir` both succeed and resolve to distinct canonical
paths. A plain branch in the primary checkout is not isolation, but detecting the primary checkout is a
**self-healing transition**, not a user-facing stop: before any Muster state write, record the source root,
source HEAD, base branch, and SHA-256 digests of the regular-file batch inputs (`.muster/backlog.md`, plus
present `.muster/manifest.json`, `.muster/STATE.md`, and `.muster/rubric.md`); reject symlinks, special files,
or a dirty tracked source tree; then create or reuse a dedicated registered driver worktree under
`.worktrees/go-backlog-<source-head-prefix>/` on a non-base `muster/go-backlog-<source-head-prefix>` branch.
Reuse is allowed only when `git worktree list --porcelain` proves the exact canonical path, branch, common
Git directory, and source HEAD; otherwise choose a collision-free suffix and run `git worktree add`, never
delete, reset, or repurpose an existing path or branch. Copy the proven batch inputs as regular files into
the driver, change every subsequent command's cwd to that driver, and repeat both `git rev-parse` checks,
the non-base-branch check, and the source-HEAD check there. Continue the batch automatically after those
checks pass. Refuse writes and stop only when creation, safe reuse, input transfer, or verification fails.
The originating primary checkout is never a product-code write surface. It is only a coordination mirror:
publish each changed backlog back through the bundled `backlog-publish --expect <source digest>` CAS path
and copy the final STATE ledger only after verifying its previously recorded digest; a concurrent change
fails closed and leaves the complete authoritative copy in the driver worktree for recovery.
Every per-item implementation/review leg and every integration leg must likewise run from its verified
isolated worktree; repeat the check after changing cwd and never use the main checkout as a write surface.
Before dispatching any writer, propagate the batch fence into that writer's cwd as regular files: create
or renew the isolated worktree's `.muster/run-active` lease and copy the batch's exact top-level set into
its `.muster/forbidden-actions`. Verify both from the worker cwd; never rely on the outer worktree's markers
and never symlink them. Renew the lease while the worker runs, then remove both propagated files only after
the worker stops or its wave reaches the barrier.

**Wave mode**

Triggered when the FILE-backlog path's `sprint-waves` call returns `ok:true` with `annotated:true`; waves replace steps 2-3's flat queue — step 4's single attended stop and both step 3 overrides still apply to every item.

- **Wave loop** — consume `sprint-waves`'s additive `schedule` field as the executable dispatch contract; do not reconstruct a disposition-split schedule from prose. Persist the full successful `sprint-waves` result as `plan`, plus adapter-observed `inFlight` entries (`itemId`, `phase`, positive `attempt`) and every mailbox `receipt` (`id`, `itemId`, `phase: implementation|review|integration`, `status: completed|failed|cancelled`, optional positive `attempt`, optional `progressFingerprint`, optional truthful `terminalReason`). Drive the batch with `$MUSTER_CLI sprint-reconcile <progress.json>` in a strict **reconcile → dispatch → wait** loop: after every wake, drain ALL currently available mailbox completions into `receipts`, reconcile once, dispatch every returned `actions` entry and reflect it in `inFlight`, then reconcile again before any idle wait. `next: dispatch` forbids waiting; `next: terminal|blocked|invalid` ends the loop; only `wait.eligible:true` permits the adapter's native wait. A blocked transition preserves its deterministic terminal reason. Duplicate receipts are idempotent, early receipts remain retained until their prerequisites arrive, and failed/cancelled/missing receipts never satisfy a dependency. A newer repaired implementation makes an older failed review stale and immediately surfaces another independent review; changing failure fingerprints permit configured recovery, while repeated identical fingerprints stop deterministically. This transition is executable and authoritative; actual Agent/Workflow/spawn/wait calls remain adapter-owned. Per wave, dispatch **every ready item regardless of disposition** as an isolated item-runner implementation leg, then the automatically surfaced review action, using the emitted cap/degradation metadata. The runner's reviewed commit/branch receipt may supply both implementation and review completion receipts when that harness keeps those legs inside one runner; reconcile still applies them phase-by-phase. `merge-local`/`merge-push` affect only the ordered integration phase and never remove an item from the concurrent build set. Use subagent type `muster-runner`, the dispatchable single-item lifecycle agent (its def carries the dispatch contract: brief inputs, receipts, gate rules); when the running session's registry doesn't carry that type (e.g. the plugin's agents were installed after the session started), fall back to a generic subagent with the same brief injected, per the orchestrator skill's generic-subagent fallback, and note the degradation in STATE — each dispatched with `isolation: "worktree"` on the Agent tool call (Claude Code's native per-subagent git-worktree isolation, branched by default from the base — see docs/research/reference-harness-design.md's `cc-subagents`/B3) so the harness itself creates `.worktrees/<item-branch>`, rather than muster shelling out `git worktree add` by hand; the harness's own auto-clean-if-unchanged does not apply here since a `muster-runner` item always commits, so cleanup stays muster's job regardless (the Isolation bullet below); on a harness whose subagent dispatch carries no such parameter (e.g. Codex's `spawn_agent` has no cwd field at all — `cx-subagents`), fall back to muster's own dispatch discipline instead: shell out `git worktree add .worktrees/<item-branch> <base>` before dispatch and verify the runner's branch/base from its own return receipt (`<item-branch>` derives solely from the item's `{id}` annotation, not raw item text — `sprint-waves`'s own `ID_TOKEN_RE` already rejects any `{id}` outside `[a-z0-9][a-z0-9-]*` before wave mode runs, so this path segment is always that validated token). Dispatch is capped at `MUSTER_SPRINT_PARALLEL` concurrent runners (default 5; hard ceiling 10 — values above 10 clamp to 10, and `0` is invalid and ignored, falling back to the default; wave-sized concurrency always stays within that ceiling). Reconciliation holds the emitted **build + review barrier** across the whole wave and exposes at most the next emitted `integration.itemIds` entry, in sequential backlog order, in the MAIN tree. The next dependency wave becomes dispatchable only from the post-integration completed state.
- **Stacked-fork code visibility** — `{deps}` guarantees a dependent builds on its predecessors' code in every mode: deps all merged at a barrier → fork the base; an unmerged `pr`/`keep` predecessor → fork that predecessor's branch tip, its PR opens `--base <predecessor-branch>` (stacked); multiple unmerged predecessors → fork the base and merge each tip in, a conflict escalates the item; a predecessor that escalated → the dependent escalates immediately instead of forking its partial tip. Stacked PRs merge bottom-up (the batch report orders them) — an out-of-band predecessor merge deletes/retargets its base branch on GitHub.
- **Dispatch and failure boundary** — every item-runner BRIEF selects `build-review-only` and carries disposition only as later-phase metadata; the runner must not push, open a PR, merge, or integrate. Before worktree creation or dispatch, and again after reconciliation, treat an escalated/failed/cancelled predecessor as a failed dependency: the dependent escalates immediately and never builds or forks the predecessor's partial tip. Reconciliation omits every escalated item and failed/cancelled build-review leg from disposition/integration while preserving the emitted survivor order.
- **Disposition boundary** — `pr`/`keep`/`merge-local`/`merge-push` remain integration dispositions, preserving the emitted order, but only after `all-build-review-complete`: `pr`/`keep` execute during the ordered integration phase exposed by reconciliation, while `merge-local`/`merge-push` remain deferred until step 4's explicit authenticated approval and then execute in that same order.
- **Isolation** — runners never write the main `.muster/STATE.md`; each keeps per-item STATE in its own worktree/scratchpad keyed by item id, returned in a capped raw-data report and folded into the single batch report (step 4). Runner cwd is its worktree, and the preflight above copies regular `.muster/run-active` and `.muster/forbidden-actions` files into that cwd before dispatch. `agent_id` and metadata paths do not bypass the action fence. Worktrees are removed once the item's disposition executes; an escalated item's worktree is kept for inspection. A freshly created worktree bootstraps its own `node_modules` per the runner contract's Worktree bootstrap rule (`plugin/agents/muster-runner.md`) -- not reinvented here.
- **Degradation** — a harness that cannot dispatch parallel runners executes the same build/review schedule sequentially in isolated worktrees, then performs the same barrier and emitted integration order; dependency-wave order stays exactly as planned. Record this selected degradation in STATE. A missing parallel primitive may serialize dispatch, but it never restores the old disposition split.

**Unattended (Routine) mode**

Steps 1-3 run identically, except step 3's step-8 disposition follows go's unattended rule per item: `merge-local`/`merge-push` downgrade to `pr` with a note in STATE and the batch report — never push to a base branch. Step 4 has no stop at all: write the batch report to STATE and exit.

**Coordination**

**Coordination model** — when a backlog/label may be worked by more than one runner at once (parallel go-backlog invocations, or humans and agents both on the same `issues:<label>`), load the **coordination** skill before step 1: CLAIM an item before touching it, leave a RECEIPT on every state change (CLAIMED/DONE/BLOCKED/HUMAN-HOLD/FAILED/YIELD/IDLE), scan BLOCKED and HUMAN-HOLD items for an answer before claiming new work, and keep exactly one LEDGER heartbeat per runner. BLOCKED resumes on any reply. HUMAN-HOLD's resume depends on the binding: Binding A resumes on a reply from the specific GitHub login recorded as `authorizer=<login>` — GitHub authenticates that authorship, so an unattended batch can trust it. Binding B has no such authentication (a STATE line is just text any writer can produce), so a written `ANSWER <slug> by <authorizer>: ...` line alone is not sufficient: resume requires an attended session presenting the held question to a human via **AskUserQuestion**, with this driver itself writing the `ANSWER ...` line to STATE only AFTER that human answers. This mode's own **Unattended (Routine)** variant has no session to ask, so it skips that resume too — a Binding B `{human-hold:}` item stays **permanently parked** across an unattended batch, exactly like `/muster:runner`. **Coordination is orchestrator-level**: only the top-level go-backlog driver (this invocation) claims items, writes receipts/ledger, and flips labels/annotations — wave mode's per-item worktree runners (Isolation, above) leave coordination state to the driver alone; the driver writes each item's CLAIM annotation/receipt itself, before dispatching that item's worktree runner (the lock always precedes any work, applied immediately rather than deferred to wave-end), then transcribes each runner's returned outcome into its DONE/BLOCKED/HUMAN-HOLD/FAILED receipt and the ledger once the wave completes, preserving the Isolation rule that only the driver touches the main STATE. The FILE source binds via backlog.md annotations (`{claimed: <runner>@<ts>}`, `{blocked: <slug>}`), composing with the existing `{id}/{deps}/{disposition}/{escalated}` grammar, with receipts/ledger in STATE's `## Coordination` section. The `issues:<label>` source binds via labels (`agent:todo`→`agent:working`→`agent:needs-input`/`agent:review`→`agent:done`), with receipts as structured `gh issue comment`s and the ledger as one pinned issue, one comment per runner edited in place. A single-runner batch may skip the claim/scan steps — nothing to race against — but should still leave receipts for audit.

**Validate a binding** — validate a fresh binding before trusting it on a real backlog: **bootstrap** (Binding A only — create the `agent:*` and ledger labels once, idempotent to re-run), then 3 smoke items: **hello-world** (claim → done, full receipt trail intact), **blocked→resume** (block with a question, answer it, confirm the next scan resumes it ahead of any fresh item), **failed** (force a failure, confirm the item reverts to claimable with a legible failure receipt).

Glass box: the sprint section in STATE, each item's branch/commits/escalations, and the final batch report are all recorded as the batch runs.
